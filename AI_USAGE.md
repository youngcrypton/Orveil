### 2.1 Core Operational Guardrails Imposed on the AI
1. **Zero Mocks Standard (`GEMINI.md §1`)**:
   Under no circumstances was the AI permitted to author mock contracts, mock precompile shims, or synthetic test doubles. Every test had to execute against live QoreChain Diana Testnet infrastructure (`https://evm-testnet.qore.host`, chain ID `9800`) and real cryptographic libraries (`@qorechain/qoresign`, `@qorechain/sdk`, `@qorechain/pqc`).
2. **Mandatory Human Escrow & Signing Gate (`GEMINI.md §2`)**:
   The AI possessed zero wallet private keys and zero custody of funds. The deployer account (`0x7DE7d6CC73002f44A76334392555C9A4dDc0B561`) and Cosmos address (`qor10hnadnrnqqh5ffmrxsuj24wf5nwupdtp0zw8kt`) were maintained solely by Damian and Young Crypton.
3. **Commit Attribution & Review Gate (`GEMINI.md §3`)**:
   Autonomous commits were strictly forbidden. Every single commit was explicitly reviewed, approved, and attributed to the respective human author (`--author="youngcrypton <goodyemegbue@gmail.com>"` or `--author="Damian <Oludegbeopemipo@gmail.com>"`).
4. **Sub-Phase Execution Lifecycle (`GEMINI.md §8`)**:
   Work was strictly partitioned into discrete sub-phases following an incremental engineering loop:
   $$\text{Explain (Mental Model)} \longrightarrow \text{Task Prompt Contract} \longrightarrow \text{Test-Driven Build} \longrightarrow \text{Post-Audit Narrative} \longrightarrow \text{Human Commit Gate}$$

## 3. Comprehensive Chronological Build Journey (Phase 0 ➔ Phase 4)

The collaboration between the human architects and the AI agent covered the entire protocol lifecycle:

### Phase 0: Toolchain Foundation & Live Cryptographic Grounding
- **Human Contribution**:
  - Identified compiler bottleneck: classical Solidity compilers trigger "Stack too deep" when passing 4,627-byte post-quantum signatures and calldata. Directed the AI to configure Solidity `viaIR: true` with 200 optimizer runs.
  - Formulated the Diana consensus minimum gas floor requirement ($\ge 0.1\text{ uqor} = 100\text{ gwei}$).
- **AI Agent Execution**:
  - Calibrated `hardhat.config.ts` and authored `contracts/interfaces/IPQCVerifier.sol` matching precompile `0x0000000000000000000000000000000000000a01`.
  - Authored `test/sdk-connection.test.ts` (10 passing tests) proving live on-chain staticcall verification of 4,627-byte ML-DSA-87 signatures directly on Diana Testnet.

### Phase 1: Settlement Contracts & Merkle Withdrawal Engine
- **Human Contribution**:
  - Architected the multi-asset settlement vault (`OreVeilSettler.sol`) supporting native QOR (`address(0)`) and testnet ERC-20 tokens (`fUSD`, `fETH`, `fBTC`).
  - Designed the 5-dimensional domain-separated Merkle leaf formula to prevent cross-chain and cross-asset replay exploits:
    $$\text{Leaf} = \text{keccak256}(\text{block.chainid} \parallel \text{withdrawalIndex} \parallel \text{recipient} \parallel \text{assetAddress} \parallel \text{amount})$$
  - Mandated the critical `returnData.length == 32` guard on line 169 to neutralize EVM empty-return vulnerabilities on uninitialized addresses.
- **AI Agent Execution**:
  - Implemented `contracts/OreVeilSettler.sol` with OpenZeppelin `SafeERC20` and `ReentrancyGuard`.
  - Authored comprehensive test suites `test/unit/OreVeilSettler.test.ts` and `test/unit/MerkleWithdrawal.test.ts` (20 unit tests) covering valid anchors, forged signatures, monotonic sequence gaps, and double-spend replay rejection.

### Phase 2: Post-Quantum Sealing & FBA Matching Engine
- **Human Contribution**:
  - Designed the discrete-time Frequent Batch Auction (FBA) clearing mechanism with 5-second uniform price epochs to eliminate toxic MEV, front-running, and sandwich attacks.
  - Selected NIST FIPS 203 (ML-KEM-1024 / Kyber-1024, 1,568-byte ciphertexts) coupled with AES-256-GCM and Additional Authenticated Data (AAD) for client-side envelope sealing.
- **AI Agent Execution**:
  - Implemented `client/orderClient.ts`: Client-side lattice encapsulation and AES-GCM envelope assembly.
  - Implemented `sequencer/matchingEngine.ts`: Ingests envelopes, decapsulates shared secrets, computes supply/demand curves, derives the Uniform Clearing Price, and builds Sparse Merkle Trees.
  - Implemented `sequencer/batchSequencer.ts`: Assembles batch commitments and signs using NIST FIPS 204 (ML-DSA-87, 4,627 bytes).
  - Authored engine test suites (`test/engine/`), verifying 100 random orders cleared at identical prices with zero slippage.

## 5. Ecosystem Extension: The OreVeil MCP Toolchain for Autonomous Agents

OreVeil does not just leverage AI during development—it is architected as an **AI-Native protocol for autonomous agents in the broader Web3 ecosystem**.

Using the official Model Context Protocol (`@qorechain/mcp`), OreVeil exposes a production JSON-RPC server ([`mcp/oreveil-server.ts`](mcp/oreveil-server.ts)) enabling AI agents (such as Claude, Gemini, and Antigravity) to query and verify the rollup autonomously:

```json
{
  "tools": [
    {
      "name": "oreveil_get_rollup_status",
      "description": "Inspects live Diana L1 contract state (latestBatchId, latestStateRoot, vault balance in QOR, active block number, and precompile 0x...0a01 status)."
    },
    {
      "name": "oreveil_verify_withdrawal_proof",
      "description": "Verifies Merkle inclusion proofs against on-chain batch withdrawal roots with domain-separated leaf hashing and checks replay execution state."
    },
    {
      "name": "oreveil_get_pqc_keys",
      "description": "Returns active NIST FIPS 204 (ML-DSA-87) and NIST FIPS 203 (ML-KEM-1024) public parameters and precompile address mappings."
    },
    {
      "name": "oreveil_query_pool",
      "description": "Queries live Diana Cosmos AMM pool reserves (e.g. Pool #2 constant product liquidity)."
    }
  ]
}
```

- **Run Command**: `npm run mcp:server`
- **Verification Suite**: `test/unit/McpServer.test.ts` (18/18 passing tests)

Through this toolchain, external AI agents can autonomously inspect OreVeil settlement proofs, audit vault solvency, and verify user withdrawal claims without human intermediaries.
